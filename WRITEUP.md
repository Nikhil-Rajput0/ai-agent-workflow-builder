# Write-up

## Schema reasoning

The core chain is `organizations → org_members → workflows → {workflow_steps,
workflow_triggers} → workflow_runs → step_runs`. Two design choices matter most:

1. **`org_id` is denormalized onto `workflow_runs` and `step_runs`**, not just reachable via
   `workflow_id`. Runs and step runs are the hot path for the live subscription and for
   permission checks on every poll; requiring Hasura to hop `step_run → workflow_run → workflow →
   organization → org_members` on every subscription tick would be slower and more fragile than a
   direct `org_id` column with its own index. The trade-off is a small write-time responsibility
   (the orchestrator must set `org_id` correctly when it inserts these rows), which is fine since
   only the trusted Action handlers ever write them.

2. **`workflow_triggers.webhook_secret` is a column, not a separate secrets table**, generated by
   `gen_random_uuid()` and deliberately excluded from every `select_permissions` column list. It's
   the sole credential for the webhook endpoint, so it must never be reachable through the
   GraphQL API — only through the admin-secret-authenticated function that validates inbound
   webhook calls.

`workflow_runs.context` and `step_runs.output` are JSONB rather than typed columns because step
output shapes vary completely by step type (an LLM's `{text}` vs. an HTTP call's `{status, body}`)
— forcing a fixed schema would mean constant migrations for every new step type.

## Enforcing the two permission layers differently

**Layer 1 (org + role scoping)** lives entirely in Hasura's declarative permission system
(`tables.yaml`). Every `select`/`insert`/`update`/`delete` permission for the single `user` role
is expressed as a relationship-based filter down to `org_members.user_id = X-Hasura-User-Id`
(optionally combined with `role: {_in: [...]}` for write permissions). Because this is enforced by
Hasura on every request against the database itself, it's the strongest possible guarantee against
cross-org leakage — there's no code path that can accidentally skip it, and it holds even against
direct ID guessing, since the row simply doesn't match the filter regardless of which id is asked
for.

**Layer 2a (step-type gating: `db_write`, `notify`, webhook triggers → owner-only)** is *also* a
Hasura permission, but expressed as an additional `_and`/`_or` clause on the `insert`/`update`
`check` — it's still a static, row-shape check ("is this row's `type` column one of the sensitive
ones, and if so is the caller specifically an owner"), so Hasura can enforce it declaratively too.

**Layer 2b (approval_gate resume)** cannot be expressed as a Hasura permission, because it isn't a
row check — it's "should this specific in-flight, paused run be allowed to continue," which
depends on execution state, not on the shape of the row being written. Regular users have zero
insert/update permission on `step_runs`, full stop. The `approveStep` Action handler runs with the
admin secret, looks up the caller's role in the run's org via a direct query, and only if that role
is `owner`/`editor` does it mark the step succeeded and call back into the same step-execution
engine used by `triggerWorkflowRun` to resume from the next position. Every other Action handler
(`triggerWorkflowRun`, `scheduledRunner`, `eventTrigger`) follows the same pattern: because Actions
and functions run with elevated (admin) database access, they are the one place in the system that
*must* re-verify org/role in code rather than delegating to Hasura, since nothing else stands
between them and every org's data.

## Approval-gate pause/resume

`workflow_runs.status` and `step_runs.status` both carry a `paused` value. When the orchestrator
(`executeWorkflow` in `triggerWorkflowRun.ts`) reaches a step of type `approval_gate`, it sets that
step's `step_run.status = paused`, sets the parent `workflow_run.status = paused`, and returns
immediately — no step after the gate is touched. The `step_runs` GraphQL subscription picks this
up live (no polling), so the frontend renders "paused, awaiting approval" the moment it happens and
shows Approve/Reject buttons to any owner/editor viewing it. `approveStep` is the only path that
can move the run out of `paused`: on approval it stamps `approved_by`/`approved_at`, sets both
statuses back to `running`, and re-invokes `executeWorkflow` starting at `position + 1` with the
run's previously-accumulated `context`, so steps after the gate see the same "memory" they would
have if the run had never paused.
